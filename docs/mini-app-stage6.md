# Этап 6 — управление транзакциями

Объём соответствует этапу 6 **mini-app-implementation-plan.md**: управление
транзакциями. Статистика этапа 7 и напоминания этапа 8 не реализуются здесь.
Существующие изменения этапа 5 сохранены.

## Реализовано

- Раздел «Транзакции»: список от новых дат к старым, затем по времени создания
  и постоянному ID; постраничная загрузка по 20 операций.
- Фильтры по датам (обе границы включены), категории, участнику, отдельно
  «Автор не указан»; поиск подстроки в описании без учёта регистра.
- Фильтры применяются совместно к текущему листу и всем корректным архивам
  `Transactions MM.YYYY`. Варианты категорий включают исторические категории,
  которых уже нет в Preferences. Авторские подписи не раскрывают настройки Users.
- Просмотр операции и её автора; редактирование даты, суммы, категории и
  описания/подкатегории; удаление после отдельного подтверждения и возможность
  отменить подтверждение. Формы блокируются от повторных нажатий.
- После успешного изменения/удаления список перечитывается, обновляются сводка
  и последние операции главной страницы; введённый на главной расход сохраняется.
- Backend разрешает member менять только свои операции, admin — любые, включая
  старые без автора. Автор, ID и время создания неизменяемы.
- Проверка суммы и даты переиспользует правила этапа 5. Новая категория должна
  присутствовать в Preferences; прежнюю историческую категорию можно сохранить.
  Неизменённые ячейки A–D, включая формулы, не перезаписываются.

## API

Каждый endpoint требует прежнюю проверенную авторизацию.

| Запрос | Результат |
| --- | --- |
| `GET /api/transactions` | `{items, total, next_offset}` |
| `GET /api/transactions/categories` | Категории текущих и архивных операций |
| `GET /api/transactions/participants` | Только `{author_id, author_name}` из книги |
| `GET /api/transactions/{id}` | Операция с версией |
| `PATCH /api/transactions/{id}` | Изменённая операция с новой версией |
| `DELETE /api/transactions/{id}?version=…` | `204` без тела |

Параметры списка: `date_from`, `date_to` (`YYYY-MM-DD`), `category`,
`author_id` (положительный Telegram ID) либо `unknown_author=true`, `search`,
`offset` (от 0), `limit` (1–100, по умолчанию 20). Некорректный период и
неизвестные параметры отклоняются с `422`.

PATCH принимает `date`, `amount`, `category`, `description` (по умолчанию пустая
строка) и обязательную `version` прочитанной операции. Клиент отправляет
полную форму; сервер записывает только отличающиеся поля и `updated_at`.
Поля автора, ID, времени создания и ключ создания запрещены в запросе.

Версия — SHA-256 содержимого операции, включая метаданные; суммы нормализуются,
чтобы числовые ячейки Sheets не создавали ложный конфликт из-за `1.00`/`1.0`.
Дополнительные столбцы не нужны. Версия работает и для мигрированных старых
строк без `updated_at`. Сравнение версии и запись/удаление выполняются в
одной блокировке SheetsGateway вне event loop. Используется постоянный ID,
а строка таблицы определяется заново внутри блокировки.

`403` — нет прав; `404` — операция уже удалена или не найдена;
`409 transaction_changed` — версия устарела; `422` — некорректные данные;
`503` — временная ошибка хранилища. Автоматических повторов записи нет.
При конфликте или неоднозначном сетевом результате интерфейс сохраняет
черновик и требует явной загрузки актуальной операции перед следующей записью.
Обновление предупреждает, что заменит черновик. Удалённая операция закрывается
после такой проверки, список и главная обновляются.

## Проверки и границы

Backend-тесты используют поддельные Sheets и пользователей. Проверяются архивы,
порядок и страницы, совместные фильтры, поиск, права прямых API-запросов,
неизменность автора и ID, валидация, конкурентные правки, внешнее изменение
старой строки, уже удалённая операция, временные ошибки и потерянный ответ
после успешной записи/удаления.

Frontend-тесты проверяют фильтры и страницы, права кнопок, форму и её валидацию,
двойное нажатие, подтверждение/отмену удаления, сохранение черновика при ошибках,
обновление и отсутствие доступа. Playwright проверяет мобильный браузер
в светлой и тёмной теме: фильтры, страницы, просмотр чужой операции, правку своей,
обновление главной и удаление. Все API и Telegram SDK в этих сценариях подменены.

Команды из корня проекта:

```sh
python -m unittest discover -s tests -v
cd mini_app/frontend
npm test
npm run build
npm run test:e2e
```

Сохраняется ограничение слоя Sheets этапа 3: один процесс записи. Локальная
блокировка не защищает от другого backend-процесса или ручной правки Sheets
между проверкой и записью. Изменения, уже видимые при проверке, отклоняются.
Постраничный API перечитывает книгу для каждого запроса; при одновременном
изменении списка другим пользователем можно нажать «Обновить список».

Реальная семейная таблица и клиенты Telegram в автоматических проверках
не используются. Проверка Android/iOS/Desktop с рабочим окружением остаётся
ручной проверкой. Строки без постоянного ID доступны для просмотра, но для
изменения требуется ранее подготовленная миграция этапа 3; приложение её
самостоятельно не запускает.
