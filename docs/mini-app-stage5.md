# Этап 5: главная страница и первая MVP-версия

Реализован этап 5 из `MINI_APP_IMPLEMENTATION_PLAN.md`. Разделы управления
транзакциями, расширенной статистики и настроек остаются каркасом.
Локальный запуск описан в [инструкции](mini-app-local-development.md).
Перед использованием реальной таблицы требуется миграция этапа 3.

## API

Все endpoints требуют проверенного Telegram `initData` и активного пользователя
из `Users`; локальная dev-авторизация ограничена прежними правилами.

- `GET /api/categories`: категории и подкатегории из `Preferences!B4:C43`.
- `POST /api/transactions`: создание расхода, ответ `201` с постоянным ID,
  автором и временными метками. Поля: `request_id` (UUID), `date` (`YYYY-MM-DD`),
  `amount` (положительная сумма, до 9 999 999 999,99 BYN, не более двух знаков
  после точки), `category` (из списка), `description` (необязательно, до 500
  символов). Сумма с запятой нормализуется frontend перед отправкой.
  Неизвестные поля, включая поля автора, отклоняются; автор определяется сервером.
- `GET /api/home`: месяц по `Europe/Minsk`, сумма текущего и предыдущего
  календарного месяца, абсолютное и процентное изменение, суммы категорий
  текущего месяца и последние пять операций общей книги. Операции сортируются
  по дате, времени создания и ID от новых к старым; старые авторы отображаются
  как «Автор не указан». При нулевом предыдущем итоге `change_percent = null`.
  Суммы сериализуются строками для сохранения точности Decimal.

Сводка читает текущий лист и архивы, фильтруя по дате расхода, а не имени листа.
Формат первых четырёх столбцов и существующие формулы сохранены.

## Сохранение и повторная отправка

Frontend немедленно блокирует повторную отправку и редактирование во время
запроса. После успеха очищает сумму и описание, сохраняет выбранную категорию
и обновляет сводку вместе с последними операциями. Переключение разделов
сохраняет черновик в рамках открытого приложения.

При сетевой ошибке или неоднозначном результате сохраняются исходный запрос
и `request_id`. Кнопка «Повторить сохранение» отправляет тот же запрос.
Повтор доступен даже при пустом обновлённом списке категорий: сервер сначала
проверяет наличие уже сохранённой операции, затем валидирует новую запись.
ID транзакции определяется сервером из UUID запроса и проверенного ID
пользователя; повторная запись атомарно проверяется под общей блокировкой
Google Sheets. Дедупликация переживает перезапуск backend и месячную ротацию.
Повтор с изменёнными данными возвращает `409`; другой пользователь не может
получить чужую запись через совпадающий ключ.

Обновление сводки после успешной записи — отдельная операция. Его ошибка
не превращает сохранение в неуспех; кнопка повтора обновляет только данные.
Запоздалый первоначальный ответ не перезаписывает обновлённую сводку.

Остаётся ограничение слоя Sheets: один процесс записи (как в этапе 3).
Черновик и ключ запроса frontend находятся в памяти открытой страницы;
при закрытии или перезагрузке страницы они сбрасываются.

## Автоматическая проверка

```sh
python -m unittest discover -s tests -v
cd frontend
npm test
npm run build
npm run test:e2e
```

`tests/test_home_stage5.py` использует поддельную таблицу и реальные repositories:
валидация, авторизация, сохранение, ошибки до/после записи, параллельный повтор,
перезапуск repository, ротация и контрольные суммы. Frontend-тесты проверяют
форму, двойную отправку, сохранение ввода при ошибке, обновление данных и гонку
ответов. Браузерные тесты проверяют мобильный сценарий в двух темах с
перехваченными API и отключённым сетевым Telegram SDK.
Тестовый Vite запускается на порту `5174`, отдельно от локального приложения
на `5173`, и завершается после браузерных тестов. Режим Vite `e2e` направляет
API на поддельный сервер порта `18000`, не обращаясь к рабочему backend на
`8000`; в обычной разработке адрес backend остаётся прежним.

Ручная проверка в настоящем Telegram на Android/iOS/Desktop и запись в реальную
таблицу выполняются отдельно по локальной инструкции. Они не выполняются
автоматическими тестами.
